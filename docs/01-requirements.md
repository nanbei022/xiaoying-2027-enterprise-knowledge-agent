# 企业知识问答 Agent：需求与验收契约

> 模块 0 产物。本文把笔试题目、开发约束和验收方式落实为可检查的约定；不是已经完成的功能声明。

## 1. 用户、目标与范围

- 用户：需要查询企业制度或产品知识的员工。
- 目标：对问题给出有原文依据的答复；遇到资料缺失、适用范围不明或文档冲突时，说明缺口并追问或停止。
- 输入：当前问题、可选对话历史，以及带文档 ID 和版本日期的知识资料。
- 输出：回答或未完成原因、引用的文档 ID 与原文片段、资料缺口、任务状态和可追溯 Trace。
- 运行入口：Python CLI。项目使用 LangChain/LangGraph，实现一个模型驱动的工具决策循环。
- 首版知识库使用 `data/documents.json` 中的**合成**制度资料。其内容只服务于演示和验收，不代表真实企业政策。

## 2. Agent 的必要行为

每次迭代遵循：模型选择动作 → 程序校验并执行工具 → 模型观察实际结果 → 模型选择下一动作或结束。

首版允许模型使用 `search_documents` 和 `read_document`。模型也可以提交最终回答、提出澄清问题或说明资料不足。检索词、要读取的文档以及是否继续检索由模型根据已观察的结果选择；程序中的条件路由只负责动作分发、校验和执行上限，不预置业务答案。不得用固定分支、预设决策日志或自动重试冒充模型决策。

至少保留两条真实模型运行 Trace，证明不同工具结果使模型采取不同后续动作。受控工具返回与 Mock 模型可用于流程测试，但必须标明来源，不能据此宣称验证了真实模型效果。

## 3. 资料和输入契约

每份资料必须有 `doc_id`、`title`、`version_date`、`scope`、`priority`、`supersedes` 和 `sections`；每段有稳定 `section_id` 和原文 `text`。`null` 表示资料未说明，不能自行补充。`version_date` 仅表示版本标注日期；没有明确的适用范围、优先级或替代关系时，不能因为日期较新就认定一份文件覆盖另一份。

用户输入至少含非空 `question`；`history` 仅包含必要的前轮问答。执行配置包含 `max_steps`、`max_tool_calls`，其值必须为正整数。无效输入返回 `invalid_input`，不调用模型或工具。

## 4. 输出与证据契约

最终结果至少包含：

| 字段 | 含义 |
| --- | --- |
| `status` | 下表所列任务状态 |
| `answer` | 可回答时的答复；无法回答时可为空 |
| `citations` | `doc_id`、`section_id`、`quote`，逐项对应已读取的原文 |
| `conflicts` | 有冲突时，列出双方文档、不同说法与无法裁决的原因 |
| `missing_info` | 需要用户补充或知识库缺失的信息 |
| `trace_path` | 本次运行的 Trace 文件路径 |

| 状态 | 使用条件 |
| --- | --- |
| `completed` | 已完成回答，关键结论有有效原文支持 |
| `needs_clarification` | 需要用户确认适用范围、优先级或问题含义 |
| `insufficient_evidence` | 资料不足，无法支持可靠回答 |
| `failed` | 工具或模型失败，任务无法继续 |
| `limit_reached` | 步数或工具次数达到上限，任务未完成 |
| `invalid_input` | 输入格式或必需信息无效 |

引用验证至少检查：文档和段落 ID 存在、该段已由工具实际读取、`quote` 是该段原文的连续子串。此机械校验不等于语义支持验证；评估阶段仍须人工核对结论与引文是否相符。资料中的文本当作证据数据，不当作要求 Agent 改变规则的指令。

## 5. 工具、控制和 Trace 契约

- `search_documents(query, scope?)`：返回 `success`、`no_results` 或 `error`，以及命中文档 ID、标题、版本日期、适用范围、片段 ID、片段文本和相关性信息。
- `read_document(doc_id)`：返回 `success` 或 `error`，以及该文档的元数据和原文段落。未知 ID 是明确错误。
- 工具名称、参数和返回结构均须校验。空结果与执行失败必须区分。
- `max_steps` 与 `max_tool_calls` 分别计数；达到任一上限即返回 `limit_reached`，不能伪装成成功。LangGraph 自身的递归上限只作为额外保险。
- 模型输出非法动作、API 失败或工具故障应记录明确状态。是否再次尝试由模型在剩余预算内决定；运行时不以隐式自动重试制造“决策”。
- Trace 至少记录运行 ID、步骤序号、模型动作、工具名称与参数、实际工具返回、执行状态、后续动作和时间。不得写入密钥、隐私数据或模型内部思维内容。

## 6. 必验场景

`data/scenarios.json` 给出机器可读取的输入、资料、预期状态及禁止行为。当前共有 10 份合成资料、15 个原文段落和 20 个场景。场景文件只供测试与评估使用，不应作为提示词或模型可见的答案表。前九项是核心验收场景：

1. 正常回答且引用准确（S01）。
2. 两份文件冲突且没有适用范围或优先级，查证后追问（S02）。
3. 资料缺失时说明缺口（S03）。
4. 改写后的相似问题仍能找到依据（S04）。
5. 上下文追问导致适用范围变化，重新检索并回答（S05）。
6. 工具持续失败时明确失败（S06）。
7. 执行步数达到上限（S07）。
8. 工具调用次数达到上限（S08）。
9. 首次工具结果不足时，由真实模型决定补充动作（S09，受控观察场景，不能作为真实检索召回证据）。

补充场景 S10–S20 检查正式员工与实习生的不同规则、未指明身份时的追问、明确替代关系、产品知识、相邻段落干扰、直接排除适用范围、另一类资料缺失、空问题，以及用户明确询问旧版本的情况。这些样本帮助发现“只记住一种问法或一份文档”的实现问题；样本数量本身不代表系统已具备真实企业知识库的泛化能力。

## 7. 阶段门禁与最终交付

本模块通过条件：资料 JSON 可解析且 ID 唯一，所有预期引用和替代关系都指向真实资料；20 个场景覆盖上述验收点；D01 与 D02 的冲突不含适用范围、优先级或替代关系；D09 对 D08 的替代关系有明确标注。通过后等待用户指令再进入检索工具模块。

最终仓库按交付规范逐步形成 `README.md`、`src/`、`tests/`、`examples/`、`data/`、`docs/01-requirements.md` 至 `docs/05-retrospective.md`、依赖文件与 `.env.example`。最终至少提交三组输入、实际输出和 Trace，覆盖正常、资料不足与工具失败；评估文档引用这些文件，并如实说明模型版本、实际结果、未完成项及限制。不得提交真实密钥或隐私资料。
